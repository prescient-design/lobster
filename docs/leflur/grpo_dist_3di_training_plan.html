LeFlur · GRPO RL fine-tuning · Protenix-free distribution reward

Can a distribution reward alone steer the binder interface toward Complexa?

A dense, Protenix-free shaping term rewards a generated binder for having an interface state distribution close to the per-target Proteina-Complexa reference — the distribution offline analysis showed predicts the true pass objective. This round runs two clean single-term ablations — AA-only and 3Di-only — at group size 64, with no confidence oracle, to test whether each reward drives optimization on its own.

01 Why this reward

LeFlur binders are D-3Di-state heavy and structurally monotonous at the interface; Proteina-Complexa binders are 3Di-diverse and V-dominated. Offline (D0), the distance from a design's interface distribution to a Complexa reference predicts pass rate — and beats distance to the native interface. We turn that predictive distance into a per-step RL reward so the policy learns to move its interface toward the passing distribution without paying a Protenix call every design.

Validated claim: closer interface distribution → higher pass rate (target-difficulty controlled). Against a Complexa reference the 3Di term is co-equal and independent of the AA term (z3Di = −0.244), unlike a native reference where 3Di is redundant.

02 Reward pipeline — one design

Every rolled-out design is scored with pure geometry — no Protenix call. Shown for the 3Di arm: the 3Di histogram is recomputed from the generated backbone, so structure_tokens are the true lever — not the decoder's tri_seqs. The AA arm is analogous: the same interface subset feeds a 20-AA histogram from sequence_tokens.

03 Reward composition — two ablation arms

Per-design reward is a sum of weighted, per-metric-clipped [0,1] terms. This round each arm keeps exactly one term live and everything else — including the whole Protenix confidence combo — at weight 0. With all confidence weights 0 the trainer skips the oracle entirely (confs=[None]*G), so there is no worker pool and no queue.

04 What GRPO framework worked best M1–M22

22 prior M-runs pin down the framework so these two runs don't re-litigate it. The headline: the gradients always worked — M21 reward-hacked a dense oracle-free reward in ~80 steps. What starved every ipTM run was reward quality: single-seed Protenix ipTM is noisy (σ≈0.06) and ~85% of steps had zero passers, so advantages chased noise and the mean→max gap never closed. The dense distribution reward is the direct answer to the diagnosed bottleneck, and the M15 endpoint prescription — "next lever is reward shaping or larger group / multi-target" — is exactly what group-64 + 38-target + dense-reward implements.
